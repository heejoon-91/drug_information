# 개인화 답변 캐시 전략

## 목적

사용자 질문에 대한 답변을 캐시하고 싶지만, 다음 조건이 모두 같을 때만 캐시를 재사용해야 한다.

- 사용자의 질문이 동일한 의미를 가짐
- 사용자의 상태가 동일함
  - 복용 중인 약
  - 기저질환
  - 알러지
  - 임신 여부 등 안전성 판단 요소
- 위 조건을 반영해 계산된 추천 성분 결과도 동일함

이 문서는 이런 전제를 만족하면서도 캐시 데이터가 과도하게 쌓이지 않게 하는 방법을 정리한다.

---

## 문제 정의

단순히 `query`만 기준으로 캐시하면 위험하다.

예를 들어:

- 질문은 같음: `두통에 먹을 약 추천해줘`
- 하지만 사용자 상태가 달라짐
  - 복용약 변경
  - 알러지 추가
  - 기저질환 추가
  - 임신 상태 변경

이 경우 이전 답변을 그대로 재사용하면 잘못된 추천이 나갈 수 있다.

따라서 캐시는 아래 조건을 만족할 때만 사용해야 한다.

1. 질문이 동일한 의미로 정규화됨
2. 사용자 안전 프로필이 동일함
3. 추천 성분 집합도 동일함

---

## 걱정해야 하는 점

이 조건을 엄격하게 적용하면 캐시 키 조합이 많아질 수 있다.

즉 아래 조합이 모두 달라질 수 있다.

- 질문 표현
- 사용자 복용 성분 집합
- 사용자 알러지 집합
- 사용자 질환 집합
- 임신 여부
- 최종 추천 성분 집합

이 때문에 캐시가 너무 많이 쌓일 수 있다는 우려는 타당하다.

---

## 해결 방향

해결 방법은 캐시를 포기하는 것이 아니라, 캐시를 "표준화 + 분리 + 제한"하는 것이다.

핵심은 다음 4가지다.

### 1. 캐시 키를 정규화해서 경우의 수를 줄이기

질문 원문을 그대로 캐시 키로 쓰지 않는다.

예:

- `"머리가 아플 때 먹는 약"`
- `"두통에 좋은 약"`
- `"두통약 추천"`

이런 문장을 그대로 저장하면 모두 다른 캐시가 된다.
대신 아래처럼 정규화된 키를 사용한다.

- `symptom_key = headache`

사용자 상태도 마찬가지다.
원문 문자열이 아니라, 실제 안전성 판단에 쓰이는 값만 정규화해서 반영한다.

예:

- 복용약: 약 이름이 아니라 `주성분 집합`
- 알러지: 표준화된 알러지 항목 집합
- 기저질환: 표준 질환명 또는 KCD 코드 집합
- 임신 여부: boolean

그리고 각 집합은 정렬 후 해시한다.

예시 개념:

```text
profile_hash = hash(
  sorted(current_medication_ingredients) +
  sorted(allergies) +
  sorted(chronic_diseases) +
  is_pregnant
)
```

이렇게 하면 같은 의미의 프로필은 같은 키로 묶을 수 있다.

---

### 2. 최종 답변 전체보다 중간 결과를 더 적극적으로 캐시하기

가장 중요한 전략이다.

최종 답변 문장 전체만 캐시하면 경우의 수가 급격히 늘어난다.
대신 재사용 가치가 높은 중간 결과를 쪼개서 캐시하는 것이 더 효율적이다.

추천 캐시 단위:

1. 증상 -> 성분 후보
2. 성분 집합 + 사용자 안전 프로필 -> DUR 판정 결과
3. 성분 -> FDA 제품 후보
4. 최종 답변 텍스트

이 중 가장 우선적으로 캐시할 대상은 `1, 2, 3`이다.

이유:

- 중간 결과는 재사용 범위가 넓다
- 최종 답변보다 중복도가 높다
- 캐시 수가 덜 폭증한다

즉 최종 답변 캐시는 선택적으로 쓰고, 핵심은 중간 계산 결과 캐시다.

---

### 3. TTL, 최대 개수, LRU 정책을 반드시 둔다

캐시는 무한 보관하면 안 된다.
반드시 자동 정리 정책이 있어야 한다.

권장 정책 예시:

- 증상 -> 성분 후보 캐시: `6시간 ~ 24시간`
- 성분 + 프로필 기반 DUR 판정 캐시: `1시간 ~ 6시간`
- 최종 답변 캐시: `1시간 ~ 6시간`
- FDA 제품 캐시: `6시간 ~ 24시간`

추가 제한:

- 최대 엔트리 수 제한
- 오래 사용하지 않은 캐시부터 삭제
- 조회 빈도가 낮은 캐시 우선 제거

즉 캐시는 "쌓이는 저장소"가 아니라 "자동으로 버려지는 임시 성능 계층"이어야 한다.

---

### 4. 아무 요청이나 저장하지 말고 저장 조건을 둔다

모든 요청을 캐시하면 불필요한 데이터가 많이 쌓인다.
저장 대상을 제한해야 한다.

저장 추천 조건:

- 증상 검색 결과만 저장
- 정상 결과만 저장
- 빈 결과, 에러 결과는 저장하지 않음
- 추천 성분이 일정 수준 이상 안정적으로 나온 경우만 저장
- 너무 특수한 fallback 결과는 짧은 TTL만 부여하거나 저장하지 않음

예:

- FDA fallback만으로 겨우 만든 결과
- 후보 성분 수가 너무 적은 결과
- 에러 메시지 응답
- DB/API 실패가 포함된 비정상 결과

이런 데이터는 캐시 가치가 낮다.

---

## 추천 캐시 구조

현재 프로젝트에는 아래 3단계 캐시 구조가 적합하다.

### 1단계 캐시

`normalized_symptom_key -> ingredient_candidates`

예:

```text
headache -> [ACETAMINOPHEN, IBUPROFEN, NAPROXEN]
```

특징:

- 사용자별이 아님
- 재사용률이 높음
- 캐시 폭증이 가장 적음

### 2단계 캐시

`ingredient_set_hash + user_safety_profile_hash -> dur_evaluation`

예:

```text
hash(ACETAMINOPHEN,IBUPROFEN) + hash(profile) -> safe/blocked result
```

특징:

- 개인화 판단이 반영됨
- 캐시 분기는 늘어나지만, 최종 답변 전체보다는 안정적임

### 3단계 캐시

`symptom_key + user_profile_hash + ingredient_set_hash -> final_answer`

특징:

- 가장 엄격한 캐시
- 최종 답변 문장을 바로 재사용 가능
- 경우의 수가 가장 많으므로 TTL을 짧게 가져가는 것이 좋음

---

## 캐시 폭증을 더 줄이는 방법

### 1. 프로필 전체가 아니라 "답변에 영향 주는 필드만" 키에 포함

불필요한 필드까지 넣으면 캐시가 과도하게 분기된다.

키에 포함할 값:

- 현재 복용 성분 집합
- 알러지 집합
- 기저질환 집합
- 임신 여부

키에서 제외해도 되는 값 예시:

- 사용자 이름
- 이메일
- 세션 ID
- 화면 표시용 프로필 텍스트 원문
- 추천 판단에 영향을 주지 않는 메타데이터

### 2. 집합은 정렬 + 중복 제거 후 해시

다음 두 경우는 같은 상태로 봐야 한다.

- `IBUPROFEN, ACETAMINOPHEN`
- `ACETAMINOPHEN, IBUPROFEN`

따라서 저장 전에 항상:

- 표준화
- 대문자 통일
- 중복 제거
- 정렬
- 해시

순서로 처리해야 한다.

### 3. 최종 성분 집합이 같을 때만 답변 캐시 사용

질문과 프로필이 같아도 성분 후보가 달라지면 최종 답변 캐시는 쓰면 안 된다.

즉 아래를 모두 만족해야 한다.

1. 증상 키 동일
2. 프로필 해시 동일
3. 최종 추천 성분 집합 해시 동일

이 기준을 만족할 때만 최종 답변 캐시 재사용이 안전하다.

---

## 운영 관점 권장 정책

### 캐시 저장 우선순위

1. 증상 -> 성분 후보
2. 성분 집합 + 프로필 -> DUR 판정
3. 성분 -> FDA 제품 결과
4. 최종 답변 텍스트

### TTL 우선순위

- 중간 결과 캐시: 길게
- 최종 답변 캐시: 짧게

이유:

- 중간 결과는 재사용 가치가 높음
- 최종 답변은 표현 차이와 상태 차이에 더 민감함

### 정리 정책

- 최대 캐시 수 제한
- LRU eviction
- TTL 만료 시 자동 삭제
- 특정 기간 동안 조회되지 않은 캐시 제거

---

## 현재 프로젝트 기준 결론

이 프로젝트는 개인화 판단이 강하게 들어가기 때문에 단순 query 캐시는 위험하다.

하지만 다음 방식으로 설계하면 캐시를 충분히 안전하게 사용할 수 있다.

- 질문을 정규화
- 사용자 안전 프로필을 정규화
- 최종 추천 성분 집합을 해시
- 중간 계산 결과를 우선 캐시
- 최종 답변 캐시는 짧게 사용
- TTL, 최대 개수, LRU 정책 적용

즉 정답은 "캐시를 안 쓰는 것"이 아니라:

`개인화 조건을 반영한 다단계 캐시 + 강한 정리 정책`

이다.

---

## 최종 요약

걱정한 문제는 실제로 발생할 수 있다.
하지만 아래 방식으로 해결 가능하다.

1. 질문과 사용자 상태를 정규화해서 캐시 키를 줄인다
2. 최종 답변보다 중간 결과를 더 많이 캐시한다
3. TTL, LRU, 최대 개수 제한을 둔다
4. 추천 성분 집합까지 동일할 때만 최종 답변 캐시를 사용한다

가장 추천하는 구조는 다음과 같다.

- `symptom_key -> ingredient_candidates`
- `ingredient_set_hash + profile_hash -> dur_result`
- `symptom_key + profile_hash + ingredient_set_hash -> final_answer`

이 구조면 개인화 안전성을 유지하면서도 캐시 폭증을 상당히 줄일 수 있다.
