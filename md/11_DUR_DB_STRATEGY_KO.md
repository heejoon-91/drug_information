# DUR 데이터베이스 전략 분석: 단일 테이블 vs 개별 테이블

**결론적으로, 현재 프로젝트(DUR 정보 조회 및 RAG 활용)에서는 `단일 통합 테이블(Unified Table)` 방식이 조회 성능과 유지보수 측면에서 더 효율적입니다.**

이 문서는 두 가지 접근 방식의 장단점과 조회 효율성을 비교 분석합니다.

## 1. 비교 분석

### A. 단일 통합 테이블 (Current Strategy)

모든 DUR 유형(병용금기, 임부금기 등)을 하나의 `DurMaster` 테이블에 저장하고, `dur_type` 컬럼으로 구분하는 방식입니다.

- **장점 (Pros)**
    - **조회 효율성 (Retrieve Efficiency)**: 특정 약물(성분코드)에 대한 **모든 안전 정보**를 한 번의 쿼리로 조회할 수 있습니다.
        ```sql
        SELECT * FROM dur_master WHERE ingr_code = 'D000001';
        ```
        RAG 시스템이나 UI에서 "이 약의 주의사항을 전부 보여줘"라고 할 때 가장 빠릅니다.
    - **관리 용이성**: 모델 파일 하나만 관리하면 되며, 새로운 DUR 유형이 추가되어도 스키마 변경 없이 데이터만 적재하면 됩니다.
    - **인덱스 효율**: `ingr_code`에 인덱스를 걸면 매우 빠른 조회가 가능합니다.

- **단점 (Cons)**
    - **컬럼 희소성 (Sparsity)**: 특정 유형에만 필요한 데이터(예: 병용금기의 `mixture_ingr`)를 저장하기 위해 범용 컬럼(`critical_value`)을 사용해야 하므로, 데이터 타입 강제나 직관성이 다소 떨어질 수 있습니다.
    - **테이블 크기**: 모든 유형의 데이터가 모이므로 테이블 로우(Row) 수가 많아집니다. (하지만 수백만 건 수준에서는 인덱싱으로 충분히 커버 가능합니다.)

### B. 엔드포인트별 개별 테이블 (Separate Tables)

`DurPregnancy`, `DurCombined`, `DurAgeLimit` 등 각 API 엔드포인트마다 별도 테이블을 만드는 방식입니다.

- **장점 (Pros)**
    - **명확한 스키마**: 각 테이블이 해당 유형에 딱 맞는 컬럼(예: `pregnancy_grade`, `age_limit_standard`)을 가질 수 있어 데이터 구조가 깔끔합니다.
    - **공간 효율**: 필요 없는 NULL 컬럼이 줄어듭니다.

- **단점 (Cons)**
    - **조회 비효율 (Retrieval Inefficiency)**: 특정 약물의 전체 안전 정보를 조회하려면 **7번의 쿼리**를 날리거나, 복잡한 `UNION` 연산을 해야 합니다.
        ```sql
        SELECT ... FROM dur_pregnancy WHERE ingr_code = '...'
        UNION ALL
        SELECT ... FROM dur_combined WHERE ingr_code = '...'
        UNION ALL
        ...
        ```
        이는 DB 부하를 가중시키고 응답 속도를 저하시킬 수 있습니다.
    - **유지보수 복잡도 증가**: 모델 7개, 수집 로직 7개, 시리얼라이저 7개를 관리해야 합니다.

## 2. 추천 전략 (Recommendation)

**현재 구조인 `단일 통합 테이블` 방식을 유지하는 것을 강력히 추천합니다.**

### 이유

1.  **데이터 동질성**: 분석 결과(`md/DUR_API_SCHEMA_KO.md`), DUR API들의 데이터 구조는 **약 80%가 동일**합니다. (성분코드, 성분명, 금기내용, 비고 등 공통). 굳이 테이블을 나눌 실익이 적습니다.
2.  **사용 패턴**: 서비스의 핵심 기능은 "특정 약물의 통합 안전 정보 제공"입니다. 이 경우 단일 쿼리로 모든 정보를 가져오는 것이 성능상 가장 유리합니다.

### 참고: 테이블 구조 최적화 제안

만약 `critical_value` 컬럼의 의미가 모호해지는 것이 걱정된다면, JSON 필드를 활용하는 방법도 있습니다. (MySQL 5.7+ / MariaDB 지원)

- `ingr_code` (Index)
- `dur_type` (Index)
- `common_data` (금기내용, 비고 등 공통 텍스트)
- **`detail_info` (JSON)**: `{ "grade": "1등급" }` 또는 `{ "age_limit": "12세 미만" }` 처럼 유형별 특화 데이터를 JSON으로 저장.
