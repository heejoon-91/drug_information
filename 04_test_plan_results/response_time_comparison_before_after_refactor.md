# 응답 시간 비교: 구조 변경 전후

## 목적

최근 적용한 구조 변경이 실제 응답 시간에 어떤 차이를 만드는지 측정한다.

비교 대상:

- 이전 구조: `HEAD(c0da92c)` 상태
- 현재 구조: 로컬 워크트리 변경 반영 상태

현재 구조에는 다음이 포함된다.

- 검색 실행 로직의 공용 payload builder 분리
- `/api/search/` API 추가
- 증상 선택 캐시 연결
- 개인화 최종 답변 캐시 연결

---

## 측정 환경

- OS: Windows
- Python env: `dur_env`
- 서버: `python run_uvicorn.py`
- 비교 방식:
  - 이전 구조 서버: `8002`
  - 현재 구조 서버: `8001`
- 비교 쿼리:
  - `두통에 좋은 약 추천해줘`

---

## 측정 방법

### 1. 경량 엔드포인트 비교

프레임워크/라우팅 자체 오버헤드를 보기 위해 `healthz`를 측정했다.

- 이전 구조: `GET /healthz/`
- 현재 구조: `GET /healthz/`
- 각 20회 평균

### 2. 실제 검색 비교

실제 검색 경로는 HTML 기준 동일한 엔드포인트를 사용했다.

- 이전 구조: `GET /smart-search/?q=...`
- 현재 구조 cold: 캐시 비운 뒤 첫 요청
- 현재 구조 warm: 같은 쿼리 두 번째 요청

현재 구조의 cold 측정 전에 아래 캐시를 비움:

- `symptom_selection:v1:두통`
- `symptom_final:v1:두통:*`

즉:

- 이전 구조: 캐시 없음
- 현재 cold: 캐시 미적중 상태
- 현재 warm: 같은 요청 재호출로 캐시 재사용 상태

## 측정 결과

### 1. 경량 엔드포인트

| 항목 | 이전 구조 | 현재 구조 | 차이 |
|---|---:|---:|---:|
| `/healthz/` 평균 응답 | `30.34ms` | `24.57ms` | `5.77ms` 개선 |

해석:

- 현재 구조가 약 `19.0%` 더 빠름
- 이 구간은 순수 앱/라우팅 오버헤드 비교에 가깝다

### 2. 실제 검색 엔드포인트

| 항목 | 이전 구조 | 현재 구조 | 차이 |
|---|---:|---:|---:|
| `smart-search` 1회 응답 | `7864.42ms` | `5768.24ms` | `2096.18ms` 개선 |
| `smart-search` 재요청 | `7864.42ms` 기준 | `3013.76ms` | `4850.66ms` 개선 |

추가 해석:

- 현재 구조 cold는 이전 구조 대비 약 `26.7%` 빠름
- 현재 구조 warm는 이전 구조 대비 약 `61.7%` 빠름
- 현재 구조 warm는 현재 구조 cold 대비 약 `47.8%` 빠름

## 왜 빨라졌는가

### 1. cold 요청도 빨라진 이유

현재 구조는 이전보다 다음 점에서 유리하다.

- 증상 선택 결과를 재사용할 수 있는 구조가 들어감
- 검색 실행 로직이 정리되면서 분기 처리가 더 명확해짐
- 같은 쿼리의 재사용 가능 데이터를 Supabase `search_cache`에 저장할 수 있게 됨

이번 cold 측정은 완전 무캐시 상태에서 시작했지만, 구조 정리와 캐시 경로 준비 비용을 포함해도 이전 구조보다 더 빨랐다.

### 2. warm 요청에서 큰 차이가 난 이유

현재 구조는 아래 조건이 일치할 때 캐시를 사용한다.

- 같은 증상 키
- 같은 사용자 안전 프로필 해시
- 같은 성분 해시

이 조건이 맞으면 다음 작업 일부를 건너뛸 수 있다.

- 성분 후보 재계산
- DUR 결과 재계산
- 최종 답변 재생성

그 결과, 같은 질문 반복 시 체감 속도 개선 폭이 크게 나타난다.

## 주의사항

이번 측정은 실제 외부 의존성을 포함한다.

- OpenAI
- Supabase
- FDA/API 경로

따라서 절대 시간은 항상 조금씩 달라질 수 있다.
특히 `smart-search`는 네트워크 상태와 외부 API 응답 시간 영향을 받는다.

그럼에도 불구하고 다음 결론은 유효하다.

- 경량 요청 기준 현재 구조가 더 가볍다
- 실제 검색 기준 현재 구조 cold도 더 빠르다
- 같은 요청 반복 시 현재 구조가 훨씬 빠르다

---

## 결론

이번 구조 변경은 실제로 의미 있는 성능 개선을 만들었다.

핵심 결과:

- 경량 엔드포인트: 약 `19%` 개선
- 실제 검색 cold: 약 `26.7%` 개선
- 실제 검색 warm: 약 `61.7%` 개선

특히 반복 질문이 많은 실제 사용 환경에서는 현재 구조의 장점이 더 크게 나타난다.

즉, 이번 변경은 단순 코드 정리가 아니라:

- 초기 응답도 더 빠르게 만들고
- 반복 요청에서는 훨씬 더 빠르게 만드는

방향으로 효과가 확인되었다.
